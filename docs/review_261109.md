# Architecture review, 2026-11-09

This review covers abstraction and encapsulation leaks, and anything that looks arbitrary, unneeded or
badly placed, across `core/`, `engine/`, `app/`, `utils/` and `plugins/`. It was done against
`bc3dc4b` ("make contexts into protocols"). Every claim names the line that shows it.

Findings go roughly from most to least urgent. Each one says what is wrong, where, why it matters,
and what to do about it. Items already listed under "Core fixes remaining" in `docs/todo.md` are
marked **(known)**. For those, this review only adds evidence.

**Checks run:** `uv run lint-imports` passes all 17 contracts. `uv run pyright` reports **1 error**
(finding 1).

## 1. `render.py` deleted but still imported: the app cannot start

`bc3dc4b` deleted `pyrpoc/plugins/panels/multisite/render.py`. However,
[backdrop.py:16](../pyrpoc/plugins/panels/multisite/backdrop.py#L16) still does
`from .render import levels_of, pixmap_of, rgb_of`. `import pyrpoc.plugins` raises
`ModuleNotFoundError`, and `app/window.py` imports it at startup, so `pyrpoc` does not launch.
pyright flags it. `lint-imports` does not: it passes, and still lists `render` as a layer
([pyproject.toml:212](../pyproject.toml#L212)), as does
[the multisite panel README:38](../pyrpoc/plugins/panels/multisite/README.md#L38).

The deletion looks accidental: the commit is about protocols, and nothing replaced the three
functions. **Fix:** restore the file (`git checkout 247cd9c -- pyrpoc/plugins/panels/multisite/render.py`),
or move its functions into `look.py` and update the README and the contract. See finding 25 for why
the commit hook let this through.

## 2. Library subscribers are called on a run's worker thread and touch Qt there

When a repeating run's settings change between passes, the worker thread calls `begin_part`
([executor.py:199](../pyrpoc/engine/acquisition/executor.py#L199)). `announce` then calls
`self.library.notify()` ([executor.py:180](../pyrpoc/engine/acquisition/executor.py#L180)), and
`LibraryStore.notify` calls every subscriber directly, on that thread. The subscribers include:

- `DataLibraryPanel.rebuild` ([data_library/panel.py:115](../pyrpoc/engine/data_library/panel.py#L115)),
  which clears and refills a `QTreeWidget`;
- `SourcePicker.refresh_sources` ([source_picker.py:65](../pyrpoc/utils/widgets/source_picker.py#L65)),
  in every open data panel, which rebuilds a `QComboBox`;
- `LibraryModel.schedule_purge` ([model.py:41](../pyrpoc/engine/data_library/model.py#L41)), which
  starts a `QTimer`. Qt refuses that from another thread, so auto-purge silently does not run.

Touching widgets off the GUI thread can crash, or corrupt them without any error. The first part is
safe only because `Executor.start` runs on the GUI thread. The comment in `events.py` ("these signals
carry that onto the GUI thread") is true of run status, but not of the library.

**Fix:** have `LibraryModel` own the GUI-thread side. Subscribe it once to the store, and re-emit
through a queued `pyqtSignal` (as `output_changed` already does). Panels and `SourcePicker` then
connect to that signal instead of calling `store.subscribe`. That also gives the library one
subscription mechanism instead of two (see 22).

## 3. "Stopped" and "finished" look the same once a run ends

`Executor.worker` swallows `Cancelled` and passes `error=None` to `finalize`
([executor.py:201-207](../pyrpoc/engine/acquisition/executor.py#L201-L207)). As a result, the
metadata of a stopped run is identical to that of one that finished. Three places then re-derive
the outcome, each its own way:

- `earlier_outputs` offers a stopped calibration or survey as the newest earlier output
  ([data_library/earlier.py:46](../pyrpoc/engine/data_library/earlier.py#L46)).
- multisite's `calibration_measured` and `survey_finished` refuse it again, by checking whether the
  output's content got filled ([bindings/preflight.py:39-53](../pyrpoc/plugins/programs/building_blocks/multisite/bindings/preflight.py#L39-L53)).
  The comment at the top of that file says exactly this.
- `RunnerSession` keeps a `failed` set fed by a signal, and works out `completed` from
  `run.cancel.is_set()` ([host.py:83](../pyrpoc/engine/acquisition/host.py#L83),
  [host.py:144-147](../pyrpoc/engine/acquisition/host.py#L144-L147)).

**Fix:** give `Run` and the recording one `outcome` (`finished | stopped | failed`), set in
`worker`, and save it in the metadata (format version 10). `earlier_outputs` then offers only
finished runs, the two multisite checks go away, and `RunnerSession.failed` becomes `run.outcome`.

## 4. `PreflightContext.folder` and `recordings_in_folder` exist for one consumer **(known)**

Confirmed: the only caller of `recordings_in_folder` in the codebase is multisite's `clean_folder`
([bindings/preflight.py:33](../pyrpoc/plugins/programs/building_blocks/multisite/bindings/preflight.py#L33)).
The only programs that override `Program.preflight` at all are the three multisite bases. By the
"what a thing is, not what one consumer needed" test, this fails.

Underneath it is a policy choice: the engine always picks "the newest output of a type in the
folder", and the user cannot choose which. The folder must therefore hold nothing else, so a core
hook exists to enforce that. Two ways out:

- Let the user choose which earlier recording an input reads (the engine proposes the newest).
  `clean_folder` is then unneeded, and so is `recordings_in_folder`.
- Keep the policy, but move the cleanliness check into the engine's `Preflight`, as a property of
  an `EarlierOutputField` (for example `sole_source=True`). Core then keeps `inputs` only.

## 5. `Field` carries screen settings beyond label and tooltip **(known, wider than noted)**

The todo names `label` and `tooltip`. The common rules also carry pure editor settings:
`IntField.step`, `FloatField.step` and `decimals`, `PathField.dialog_filter`
([rules.py:18, 38-39, 61](../pyrpoc/utils/value_rules/rules.py#L18)). The core README says "How a
value is edited on screen is not part of its rules", and these contradict it. `decimals` and
`step` never affect `coerce`.

If the split is ever made, these move with the tooltip into an editor hint next to the input,
while `label` stays because it names the value in error messages. Doing it piecemeal is not
worthwhile. If the split is not going to happen, change the README sentence to describe what is
true.

## 6. One concept, six names

The rules a value follows are called `Field` (the class), `rule` (`ProgramInput.rule`), `spec`
(`Editor.spec`, `spec_field`, the variable in `ConfigValues.set`), and `"param"` (the dataclass
metadata key, [device.py:37](../pyrpoc/core/device.py#L37)). Their error is `ParameterError`.
The values themselves are "program inputs" everywhere except `RecordingPart.parameters`,
`ParamForm`, and the "Parameters" heading in the details dialog. On top of that, `Field` lives in
`program_input.py` even though `DeviceConfig` uses it just as much
([device.py:15](../pyrpoc/core/device.py#L15)).

This is the "specific nouns" problem: a reader has to learn that six words mean two things.
**Fix:** move `Field` into its own `core/field.py` and call the attribute `field` (or call the
class `Rule` and use `rule` everywhere). Rename `ParameterError` to `InvalidValue`, and
`parameters` to `inputs` (format version bump). This is mechanical, and best done in one commit.

## 7. The `ProgramInputs` collection is keyed by string, so values lose their type

`ProgramInputValues.__getitem__` takes a `ProgramInput[T]` and returns `T`. However,
`ProgramInputs.get(key: str) -> Any` and `set(key: str, value: Any)`
([program_input.py:87-93](../pyrpoc/core/program_input.py#L87-L93)) do not. Nine call sites
write `inputs.get(X.key)` or `inputs.set(X.key, ...)`, and some re-annotate the result by hand
(`LoopFeed.given`, [feed.py:153-155](../pyrpoc/plugins/panels/multisite/feed.py#L153-L155)).
A typo in a value's type gets past pyright here and nowhere else.

**Fix:** add typed `get(program_input: ProgramInput[T]) -> T` and `set(program_input, value: T)`,
and keep the string forms internal to the engine (session load, the inbox).

## 8. Outputs are addressed by string and type at every use

A program declares `emits = {"intensity": ImageOutput}`, then writes
`ctx.output("intensity", ImageOutput)` at each use
([confocal/program.py:41](../pyrpoc/plugins/programs/confocal/program.py#L41)). The name and the
type are repeated, and only checked at run time
([program.py:164-176](../pyrpoc/core/program.py#L164-L176)). Inputs got typed declarations
(`declare` → `ProgramInput[T]`), but outputs did not.

**Fix:** use a small `OutputSlot[T](name, type)` declared beside the program, so that
`emits = [INTENSITY]` and `ctx.output(INTENSITY)`. Do this when output naming next changes; it is
a consistency improvement, not urgent.

## 9. Programs alone are not stamped with their key

`device_registry`, `program_output_registry` and both panel registries stamp the key on the class.
`program_registry` does not (`stamp=None`,
[program.py:195](../pyrpoc/core/program.py#L195)), and the only reason given is "Programs keep
their key at the registration site". As a result, the key travels next to the program everywhere:
`Start.program_key` and `Start.program` ([preflight.py:35-36](../pyrpoc/engine/acquisition/preflight.py#L35-L36)),
`RunnerHost.attach(key, program)`, and `RunnerSession.key`.

**Fix:** stamp `registry_key` like the others, and drop the parallel `program_key` arguments.

## 10. Earlier outputs are "an input like any other", yet the engine special-cases them

The core README says an earlier output "is a program input like any other". In practice the
engine finds them by `isinstance(rule, EarlierOutputField)`
([acquisition/earlier.py:20-22](../pyrpoc/engine/acquisition/earlier.py#L20-L22)) and handles them
specially in three places:

- `fill_earlier`;
- the `earlier_outputs` check in `Preflight` ([preflight.py:91-103](../pyrpoc/engine/acquisition/preflight.py#L91-L103));
- the Acquisition panel, which refreshes them when a form is built
  ([panel.py:191-193](../pyrpoc/engine/acquisition/panel.py#L191-L193)).

The engine depending on one particular rule from `utils/value_rules` contradicts "nothing
specific" in core's terms. It is allowed by the layers, but the concept is spread over five files:
`utils/value_rules/rules.py`, `plugins/program_io/inputs/earlier.py`, `engine/acquisition/earlier.py`,
`engine/data_library/earlier.py`, and `multisite/bindings/earlier.py`.

**Fix:** either say plainly in the README that earlier outputs are a kind of input the engine fills
(and move `EarlierOutputField` into `core/` next to that statement), or turn "a value the engine
fills from the save folder" into a small `Field` protocol the engine calls, so the engine stops
naming the class.

## 11. An earlier output held as an input value lives outside the library's memory limit

`fill_earlier` loads an earlier recording from disk and keeps it out of the library on purpose
([acquisition/earlier.py:67-68](../pyrpoc/engine/acquisition/earlier.py#L67-L68)). Its output then
sits in `ProgramInputsStore` as a value. Two consequences:

- A survey's overview and tiles, or a calibration's frames, take memory that the Data Library's
  size and limit do not show.
- When the input holds the library's open copy, closing that recording in the Data Library does
  not free it, because the input still references it.

**Fix:** if finding 10 is taken on, hold a reference (recording path and output name) as the value,
and resolve it to content at run start. Otherwise, count these copies in the library's total.

## 12. Three device flags encode one choice

`owns_connection`, `holds_session` and `backed_by` ([device.py:62-71](../pyrpoc/core/device.py#L62-L71))
combine into four real kinds: kept session (Andor, Prior, Toupcam), testable (DAQ, Time Tagger),
backed (galvo, simulated scanner), and none (simulated dish). The DAQ's own comment says
`owns_connection` "means the card can be verified, not that it holds a handle"
([daq/device.py:4-5](../pyrpoc/plugins/devices/daq/device.py#L4-L5)), so the name misleads.

The inventory and the Devices panel branch on the flag combinations
([device_inventory/panel.py:31-44](../pyrpoc/engine/device_inventory/panel.py#L31-L44)), and
`test_device` has a branch no menu can reach
([inventory.py:126-127](../pyrpoc/engine/device_inventory/inventory.py#L126-L127)).

**Fix:** use one `connection: Connection` enum (`SESSION | TESTABLE | NONE`), with `backed_by` kept
separate since it is about claims, not connecting.

A related point: a backed device knows its backing class but not its backing instance, so programs
fetch the DAQ on faith that a claim brought it along
([galvo_pinpoint/program.py:38-40](../pyrpoc/plugins/programs/galvo_pinpoint/program.py#L38-L40)).
That is fine while there is one DAQ, but should be noted for "dual galvo" on the todo list.

## 13. The device inventory holds screen state

`DeviceInventory` holds `open_panels` and a `panel_requested` signal that "the window does"
([inventory.py:36-44](../pyrpoc/engine/device_inventory/inventory.py#L36-L44)), and the session
saves `panel_open` in `WorkingState.devices` ([session/file.py:29](../pyrpoc/app/session/file.py#L29)).
Rule 4 says screen state and working state are kept apart. Whether a device's panel is open is
screen state.

**Fix:** move `open_panels`, `panel_requested` and `set_panel_open` into `app/device_docks.py`, and
save open device panels under `ScreenState`. The Devices panel would ask `DeviceDocks` (through a
small protocol) instead of the inventory.

## 14. The run inbox's subscription is opened by the executor and closed by Qt code

`Executor.start` creates the `RunInbox`, which subscribes to the program inputs
([inbox.py:51](../pyrpoc/engine/acquisition/inbox.py#L51)). It is unsubscribed by
`Runs.on_run_finished`, a Qt slot ([runs.py:150](../pyrpoc/engine/acquisition/runs.py#L150)). The
executor says it has "No Qt, so runs can be driven without a QApplication"
([executor.py:4](../pyrpoc/engine/acquisition/executor.py#L4)), but driven that way, every run
leaves a subscriber behind.

The ownership is split for a real reason: posts and the close must happen on the thread that sets
inputs. **Fix:** let the executor own the close, and have it marshal the close onto the posting
thread through a callable it is given, such as `RunCallbacks.on_closed`. Then the object that opens
the subscription also closes it.

Nearby, `RunEvents` both declares signals and starts runs, and `Runs` reaches through it with
`self.events.executor.preflight(...)` ([runs.py:82](../pyrpoc/engine/acquisition/runs.py#L82)).
`Runs` could own the `Executor` directly, with `RunEvents` reduced to the signals.

## 15. Run status is stringly typed

`status_dot` picks the colour by whether the status text starts with "needs", "error" or
"acquiring" ([acquisition/panel.py:47-55](../pyrpoc/engine/acquisition/panel.py#L47-L55)). A
program whose `ctx.status` text happens to begin with "error" shows red, and rewording "needs"
anywhere changes the colour. `Taken.kind` is the same pattern ("input" or "device",
[format.py:34](../pyrpoc/engine/data_library/format.py#L34)).

**Fix:** use a small `Status(kind, text)`, or separate signals for the engine's own states
(ready, needs, running, failed), with program text always shown as running. Use a `Literal` or an
enum for `Taken.kind`.

## 16. Readiness is computed two or three times per signal, and the view writes to collections

`refresh_readiness` calls `blockers()`, then `apply_enabled()` calls `blockers()` again
([acquisition/panel.py:218-256](../pyrpoc/engine/acquisition/panel.py#L218-L256)).
`set_running_ui` calls `apply_enabled` once more. Each call builds a new `Program` instance and runs
the full preflight, which for a loop reads the scratch file and lists the folder. `readiness_changed`
fires on every input change, so drawing units or masks repeats this work constantly.

Two related points:

- `build_inputs` calls `runs.refresh_earlier()` ([panel.py:191-193](../pyrpoc/engine/acquisition/panel.py#L191-L193)),
  so building a form sets program inputs.
- `on_input_changed` reloads every editor on any key change
  ([panel.py:204-210](../pyrpoc/engine/acquisition/panel.py#L204-L210)).

The todo's bug 3 ("checks do not update when the action to pass the checks is done") lives in this
area. Readiness that is pushed rather than pulled would make it easier to see which change was
missed.

**Fix:** have `Runs` compute the blockers once per change and emit them with
`readiness_changed(list[str])`. The panel caches them. Folder refresh belongs in `select_program`
on the `Runs` side, not in the view.

## 17. Rule 3 ("every panel is equal") is not true of the code

The window treats panels differently in several ways:

- It has three fixed panels with their own `DockKey` and `DockSpec`, each built with different
  arguments ([window.py:36-54, 128-143](../pyrpoc/app/window.py#L36-L54)).
- Fixed panels save their state under `screen.panels`, and added panels under `screen.views`.
- `DataPanel.misc` decides which menu a panel goes in.
- The window pushes `refresh()` into data panels whose output changed
  ([window.py:198-203](../pyrpoc/app/window.py#L198-L203)), instead of panels following the
  library themselves.

None of this is wrong in itself, but the README states the opposite. **Decide:** either soften rule
3 to "no panel is special to the engine", which is true, or make it true. Making it true means one
panel registry, constructed from a shared bag of collections, with `DataPanel` subscribing to
`output_changed` itself.

## 18. Qt lives in `program_io/inputs`, so programs import widgets

Four input modules import Qt:

- `masks.py` (`thumbnail`);
- `modulation.py` (the `MaskLinesTable` editor);
- `point.py` (the `PointPicker` editor);
- `pixel_pick.py`, which imports `utils.widgets.source_picker` only to get a label string
  ([pixel_pick.py:11](../pyrpoc/plugins/program_io/inputs/pixel_pick.py#L11)).

Every program imports `program_io.inputs`, so every program, including code running on worker
threads and the multisite stages that are meant to run on fakes, pulls in Qt widgets. The "editor
beside its Field" rule in the core README is what puts them there.

**Fix:** keep the rule, but make "beside" a sibling module, for example `inputs/point_editor.py`.
Register those editors from the panels side, such as `utils/widgets/` or the Acquisition panel's
import of `program_io.editors`. Move `source_text` to a no-Qt helper. A `forbidden` contract
"program_io.inputs never imports PyQt6" would then hold it.

## 19. DAQ details in generic places

- The generic channels editor labels buttons `AI0…AI8` ([editors.py:246](../pyrpoc/utils/widgets/editors.py#L246)),
  and `ChannelsField` defaults to 9 channels. The field is generic, but its editor is the NI card's.
- `MaskLine.channel` formats an NI channel string inside a program input type
  ([modulation.py:45-47](../pyrpoc/plugins/program_io/inputs/modulation.py#L45-L47)), and
  `RigMicroscope.raster` builds the same string separately
  ([rig.py:39](../pyrpoc/plugins/programs/building_blocks/multisite/bindings/rig.py#L39)).
- Channel labels are `ai0` in `RigMicroscope` but `AI0` in the editor.

**Fix:** put one `DAQ.line_channel(port, line)` and one channel-label function on the DAQ device,
and give `ChannelsField` a `prefix` (or labels) argument.

## 20. Placement follows the layer rule, not the meaning

`Unit`, the value of the `UNITS` input, lives in `program_io/outputs/units.py`, because inputs may
import outputs but not the reverse. `Mask`, by contrast, lives in inputs. A reader looking for "what
a unit is" would not look under outputs. The same pressure put the earlier-output declarations in
`inputs/earlier.py`, which imports outputs.

**Fix:** add a third bottom layer, `program_io/values/` (value types such as `Unit`, `Mask`,
`Point`, `ScanGeometry`), that both inputs and outputs import.

## 21. Multisite: the scratch, field size and the survey-to-loop link are worked out by hand

- The loop's scratch file is written by the program straight into the Experiment folder, outside
  its recording. The folder is found through the survey's recording
  ([bindings/loop.py:114-119](../pyrpoc/plugins/programs/building_blocks/multisite/bindings/loop.py#L114-L119)),
  and the run's own recording name through an output's `root`
  ([loop.py:136-140](../pyrpoc/plugins/programs/building_blocks/multisite/bindings/loop.py#L136-L140)),
  because `RunContext` does not say which recording it is filling. **Fix:** add the recording's name
  and folder to `RunContext`.
- One field's pixel size is derived as `survey[0].shape[-1]` in three places: preflight, `field_of`,
  and `LoopFeed.field_um`. **Fix:** give `SurveyOutput` a `field_pixels` property.
- The Multisite panel finds "the loop over this survey" by comparing each recording's encoded
  parameters with `SURVEY.rule.encode(survey)` ([feed.py:63-69](../pyrpoc/plugins/panels/multisite/feed.py#L63-L69)).
  That works, but it is a reverse lookup the data model does not offer, and the panel is a
  `DataPanel[SurveyOutput]` that mostly shows other outputs. If more panels need this, "recordings
  that read this output" belongs next to `Library`. It is also the problem the todo's "panels
  declare what they take in" idea is circling.

Each copy is small. Together they are why the same behaviour differs slightly from one place to

Also in this group:

- `Registry` has no `__contains__` or `__iter__`, so callers either reach into `.entries`
  ([grouping.py:19](../pyrpoc/engine/data_library/grouping.py#L19),
  [device_panel.py:52](../pyrpoc/utils/widgets/device_panel.py#L52)) or test membership against a
  freshly sorted list ([format.py:199](../pyrpoc/engine/data_library/format.py#L199)). The ruff
  `SIM118` ignore in `pyproject.toml` exists only because of this. Adding the two methods would
  let it go, but that is a config change, so it is your call.
- `LibraryModel` re-exposes most of `LibraryStore`, while the executor talks to the store directly.
  `relay_new_outputs` re-subscribes every output of every recording on each notify.

## 23. Two simulation stacks across three folders

The simulated dish is split three ways: the model in `utils/simulation/`, the devices in
`plugins/devices/simulated/`, and the programs in `plugins/programs/simulated/`. Alongside it,
`programs/simulated/` holds a second, older fake-data stack (`synthetic_detector.py`, `signal.py`,
`specimen.py`, `mosaic_simulation/slide.py`) used by `Simulation` and `MosaicSimulation`.

Two ways of faking an instrument means two things to maintain and two results that cannot be
compared. Simulated programs also register in a `register()` function while everything else
registers where it is defined. The reason given is that their inputs must not exist without
`--simulated`.

**Decide:** retire the fake-data programs in favour of the dish, or say in
`programs/simulated/__init__.py` why both are kept.

## 24. Dead code, unused defaults, stale docs

- `Galvo.summary()` and `SimulatedDish.summary()` have no callers.

## 25. Tooling: nothing before push would have caught finding 1

The commit hook runs ruff and import-linter, while pyright runs only in CI on push. A deleted
module that is still imported passes both hook checks: ruff does not resolve imports, and
import-linter ignores modules it cannot find. **Suggestion:** add a fast smoke check to the hook,
`uv run python -c "import pyrpoc.plugins"`. It is a check, not a test, and takes about a second.
Alternatively, run pyright on staged files only.

## What holds up well

These parts are sound, and changes should keep them:

- **The layering is enforced.** 17 import contracts pass, and the multisite stages really run on
  fakes.
- **Registries replace lists.** Nothing enumerates plugins.
- **Preflight is one judge.** It lists every blocker at once, and the start re-asks under the lock.
- **The inbox has clear rules** about when an edit is taken.
- **Validation sits at the boundaries.** Nearly every `isinstance` and `try` in the code is at
  session JSON, files or hardware.
- **Function size is kept.** One function in the whole package is over 45 lines.
